# Threat model

STRIDE analysis per trust boundary, with what actually mitigates each threat and
an honest account of what does not.

This document is written against the code as it exists, not against an intended
design. Where a mitigation is partial, the "Residual risk" column says so; where
there is none, it says that too. A threat model whose right-hand column is
uniformly "mitigated" is describing a diagram, not a system.

Read [the security model](model.md) first for the boundaries and the
guarantee → test table. The boundary numbering here matches it.

**Assets, in rough order of what an attacker wants:** brokered credentials
(GitHub PATs, kubeconfigs, registry logins), the hub's secret-sealing key,
arbitrary code execution on the hub host, the project state database, the audit
trail's integrity, and the hub's network position (its egress reachability into
private networks).

**Standing assumption:** *the workload is hostile.* It runs code an LLM chose. So
"a task did something malicious" is not a compromise of this model — it is the
scenario the model is designed for. The question is always what the blast radius
is.

## ① Browser ↔ hub

| STRIDE | Threat | Mitigation | Residual risk |
| --- | --- | --- | --- |
| **S**poofing | Attacker authenticates as another user | OIDC ID token verified against provider JWKS (RS256/ES256), issuer and audience checked; session cookie is `HttpOnly` so JS cannot read it. The static bearer token can be retired at runtime — Settings → Static admin token, or `cloop hub token static retire` — and every hub member refuses it from then on, in the header and as `?token=` alike, with a `401` saying when and by whom it was retired and what to present instead; refusals do not count toward the guess lockout, and a member that starts reads the retirements before it serves (`TestStaticToken_RetiredIsRefusedOnTheRetiringMember`, `TestClusterStaticTokenRetirementReachesEveryMember`, `TestStaticToken_RetirementSurvivesARestartAndANewValueIsAdmitted`). Retirement is per value, so deploying a new one is the rotation path; a token-only hub stays closed after its token is retired, and retiring it with no SSO and no admin API token is refused unless forced (`TestStaticToken_TokenOnlyHubStaysClosedAfterRetirement`, `TestStaticToken_RetireRefusesToStrandATokenOnlyHub`). One function, `checkStaticToken`, compares the token for both authentication gates (`TestStaticTokenIsComparedInOneFunction`). `cloop hub doctor` warns `ui.static_token` while one is accepted beside an enforced role policy, saying how long it has gone unused (`TestStaticTokenAcrossTheMatrix`) | Until it is retired the static token is a bearer credential with **admin** rights and no expiry — anyone holding it is admin, outside RBAC. Use SSO where you can, treat the token as a root password, and retire it once SSO works. A member that reads no hub bus (`ui.cluster.exclusive`) refuses a retirement made elsewhere within 30 s |
| **E**levation of privilege | Anyone on the network drives a hub that has no sign-in: lists its projects, queues tasks, starts agent runs on its host | A hub with neither `ui.oidc` nor a static token listens on `127.0.0.1` unless an address is named, and an address beyond loopback is refused at startup — before the hub touches its control plane — unless `ui.allow_unauthenticated_network` acknowledges it, in which case it warns at every start (`TestBindAddressForEveryAuthAndListen`, `TestUIBindAddressMatrix`, `TestRunRefusesAnOpenHubBeyondLoopback`, `TestAnOpenHubNeverListensBeyondLoopback`); the built binary is unreachable on the host's own network address and refuses `--listen 0.0.0.0` (`TestE2EOpenHubIsNotReachableBeyondLoopback`, `TestE2EOpenHubRefusesANetworkAddress`). Loopback is read from the address, never resolved (`TestLoopbackIsDecidedFromTheAddressNotTheResolver`). `cloop hub doctor` fails `ui.exposure` for a hub without sign-in that its socket table and an unauthenticated request show is reachable beyond loopback, whichever build serves it (`TestExposureFailsAnOpenHubOnTheNetwork`), and warns for a signed-in hub serving plaintext beyond loopback behind an https URL (`TestExposureWarnsOfPlaintextBehindHTTPS`) | Loopback is not a credential: every local user and process can still drive an open hub. A page in a browser on its host cannot — it is refused by origin, by media type and, under a rebound name, by Host (the two rows below). The acknowledgement re-opens it by design. The rule governs the hub's own socket, not what forwards to it: a container runtime publishing the port, or a reverse proxy that does not authenticate, re-exposes a loopback hub. An API token is not sign-in — a hub whose only credentials are API tokens serves callers that present none. A build from before the rule binds every interface whatever its configuration; only stopping it or a firewall closes that, and the doctor names it |
| **S**poofing | Stolen session cookie replayed | `HttpOnly`; `Secure` + `SameSite=Strict` under TLS. A session is a server-side row keyed by the cookie's SHA-256, and it ends at its absolute TTL (`ui.oidc.session_ttl_hours`, 24 h), after `idle_timeout_hours` unused (8 h), when the IdP refuses its refresh token (asked every `refresh_interval_minutes`; needs `CLOOP_SECRET_KEY`), on sign-out, or when revoked — by its user (`POST /api/session/logout-all`), from the Sessions panel (`DELETE /api/sessions/{id}`, `session.admin`), or from a shell (`cloop hub session revoke` with a session id, `--identity` or `--all`; `cloop hub user offboard`) (`TestRevokeThenRequestIsRefused`, `TestIdleTimeoutEndsSession`, `TestRevokedSessionIsRefusedOnNextRequest`). Every WebSocket, SSE stream and sandbox terminal the cookie opened ends with it, by any of those causes (`TestStreamCredentials_EveryEndingClosesEveryChannel`, `TestAttach_ARevokedSessionClosesItsTerminal`). **Sudo mode** (Task 20448): a live cookie is not enough for a privileged action — creating or deleting a secret or a grant, approving a grant request or an API token, minting an API token or an executor enrollment token, editing `ui.oidc` (role mappings, `require_rbac`), retiring the static token, rotating the hub CA, upgrading or deregistering an executor, attaching to a sandbox, granting membership at maintainer, ending somebody else's session, offboarding, minting a SCIM credential or a display-glasses link, setting a provider's API key or base URL, the dictation key or the CI relay's settings. Those also need the person behind the session to have authenticated interactively within `ui.oidc.sudo_max_age_minutes` (2 h): the id_token's `auth_time`, or a sign-in the hub itself started with `prompt=login`; silent renewal and the server-side refresh never count, and the time is on the durable session row, so every member agrees. Older, the request is refused with 401 `REAUTH_REQUIRED` — never a bare 403 — and the dashboard's "Confirm it's you" dialog sends the person to the provider with `prompt=login&max_age=0`; a token whose `auth_time` predates that request, or another account, is refused. The confirmation creates a new session in the browser that signed in, so a stolen cookie whose owner is phished into completing one stays as stale as it was. The route table declares the rule beside each permission and the gate enforces it (`TestPrivilegedRoutesAskForARecentSignIn`, `TestStaleSessionMustConfirmItsYouForPrivilegedActions`, `TestConfirmItsYouRefusesAProviderThatDidNotAsk`, `TestSilentRenewalDoesNotRefreshTheSignIn`, `TestClusterMemberHonoursAFreshSignInMadeOnAnother`, `TestConfirmItsYouDialogInBrowser`); every refusal is counted (`cloop_session_reauth_total`) and audited as [`session.reauth`](../reference/audit-events.md#session) | No device binding: the IP and user agent are recorded, not checked, so a stolen cookie works from anywhere until one of those ends it — for everything but the privileged actions, which it can take only within `sudo_max_age_minutes` of its owner's last interactive sign-in. And using it keeps the idle clock running, so unnoticed it lasts to the absolute TTL; an open tab's streams do not (`TestCheckSessionLeavesTheIdleClockAlone`). `sudo_max_age_minutes: -1` turns sudo mode off, and `cloop hub doctor` and Hub health warn (`oidc.sudo`). A provider that reports no `auth_time` (Entra ID unless the optional claim is configured) is trusted to have asked when told `prompt=login`, and an ordinary sign-in on such a provider is never recent, so the first privileged action after it asks. API tokens and the static token are not sessions and are not asked: their own rows above and below bound them. A terminal session is held to the window from the sign-in behind its `cloop login` approval — the approval itself when it asked the person to sign in, which it does whenever the approving browser's own sign-in is not recent, and otherwise the browser's — so a stale browser cookie cannot mint a fresh terminal session (`TestTerminalSessionsCountFromTheSignInBehindTheirApproval`). A revocation is immediate on the hub member that made it, and reaches every other member and every stream and terminal the cookie opened within a bus poll (¼ s), the shell's included (`TestClusterCredentialEndingsCloseStreamsOnEveryMember`). A hub that reads no bus (`ui.cluster.exclusive`) honours a session revoked elsewhere for up to 30 s (its session cache) and closes what it opened at the next 30 s re-check after that |
| **T**ampering | Request forgery from another origin: a form, a `no-cors` fetch or a WebSocket on a page elsewhere drives the hub with the browser's credential — the session cookie, an authenticating proxy's cookie or Basic credential — or, on a hub without sign-in, with none | Every state-changing request (any method but `GET`, `HEAD`, `OPTIONS`) is refused with 403 `CROSS_ORIGIN` unless it carries `Authorization: Bearer` — which a page elsewhere can attach only after a preflight, and the hub grants none and sends no CORS header to anyone (`TestTheHubGrantsNoCrossOriginRead`) — or the browser's `Sec-Fetch-Site` is `same-origin`/`none`, or, without it, its `Origin` is absent or exactly one of the hub's own origins: the scheme and host it was addressed to, `ui.external_url`, the SSO callback's origin, `ui.allowed_origins`. `same-site` — another port of the hub's host, a sibling subdomain — is refused like `cross-site`. Its body must be `application/json` (multipart on the three upload routes), else 415, and every handler decodes through one decoder that refuses the rest (`TestEveryUnsafeRouteRefusesAPageElsewhere`, `TestUnsafeRoutesAdmitTheHubsOwnPagesAndBearerTokens`, `TestHandlersReadJSONOnlyThroughTheDecoder`, `TestCheckUnsafe`, `FuzzCheckUnsafe`, `TestDecode`). Both WebSocket upgrades match the `Origin` exactly — scheme, host and port; no loopback or other-port allowance (`TestWSOriginAllowed`; the agent endpoint's twin is `TestHubCheckOrigin`, and `TestHubRejectsCrossOriginUpgrade`). A real browser's text/plain form, `no-cors` fetches and WebSocket from another port and another site are all refused and write nothing, while the dashboard in the same browser adds a task and saves a setting (`TestAPageElsewhereCannotDriveAnOpenHubInBrowser`). Each refusal is counted (`cloop_cross_origin_refusals_total`) and audited as [`request.origin_refused`](../reference/audit-events.md#request) (`TestRefusalsAreCountedAndAudited`). `cloop serve` applies the same rules and grants CORS only with a token (`TestServeWithoutATokenGrantsNoPageElsewhere`) | A browser too old to send either `Sec-Fetch-Site` or `Origin` on a form POST (Firefox before 70) is stopped only by the media type, which holds for every JSON route; the three upload routes take multipart. Markup injected into the dashboard itself is same-origin and is not this row's to stop: see the next row. The audit trail takes at most 30 refusals a minute and counts the rest in the next row; the metric counts all |
| **E**levation of privilege | Markup injected through a string a workload or a peer wrote — a project's directory name, a task's title, description, result or output, a feature's or an executor's name, a USB device's product string, a member's identity, a KB entry, an AI suggestion — runs as script with the session of whoever views it; a hub admin sees every project, and script with an admin session mints tokens, binds roles and rewrites `ui.oidc`. Found live: a project named `demo&quot;+(document.title='PWNED')+&quot;` broke out of the inline `onclick` its card spliced it into (Task 20408) | Two layers. Every value is escaped where it is rendered, and markup carries no code: a control names an action in a `data-action` attribute and keeps its arguments in `data-arg*`, read as data by one delegated dispatcher whose registry is all a `data-action` can invoke — never `window`, where `fetch` lives — so the five sites that spliced a name into JavaScript now carry it in an attribute (`TestDashboard_HostileProjectNamesStayData`, `TestDashboard_EveryActionIsRegistered`). The pointer passing over an element and a drag crossing one run only what was registered for that very event, so injected markup laid over the page cannot act without a click (`TestDashboard_PassingEventsRunOnlyTheirOwnActions`). A link is a link only over http(s) (`safeURL`). And the policy stops what escaping misses: every response carries `script-src 'self'` with neither `'unsafe-inline'` nor `'unsafe-eval'`, plus `base-uri 'none'`, `form-action 'self'` and `object-src 'none'`; the theme bootstrap, the glasses app and the sign-in documents' script are assets (`TestContentSecurityPolicyOnEveryDocument`, `TestNoInlineEventHandlers`, `TestNoInlineScripts`, `TestSignInDocumentsLoadOnlyTheScript`). Chrome is driven through every tab and dialog with hostile strings in every such field and every control pressed: nothing runs and the policy blocks nothing, while a handler injected on purpose is both blocked and reported (`TestHostileStrings_EveryControlInBrowser`; with sign-on, members' identities and the signed-in user's display name: `TestHostileMemberIdentities_InBrowser`). Violations reach `POST /api/csp-report`, are counted in `cloop_csp_violations_total` and, with telemetry on, recorded (`TestCSPReportsAreCountedInBothFormats`, `TestCSPReportRecordsWithinItsBudget`) | `style-src` keeps `'unsafe-inline'` ([out of scope](#out-of-scope)). Markup a missed escape lets through still renders — a fake control, a misleading label — and can name a registered action, which a click then runs with the arguments the markup chose; so can a deferred panel's `data-act`, within that panel's own markup. Each is a dashboard action the user could take anyway and every write is still decided by the route's permission, and the destructive ones are bounded further: the GitHub App panel's controls are registry actions that run only from inside the panel — its old document-wide `data-gh-*` router let a revoke control anywhere on the page revoke a grant — and every DELETE the dashboard sends asks first, naming what it removes, either in the function sending it or as the button of a confirmation dialog no other control names; a revoke or a KB deletion naming something the panel does not show is not sent (`TestDashboard_EveryDeleteIsConfirmed`, `TestDashboard_DeletesAskFirst`, Task 20422). So a click on injected markup can at most raise that question, while a write that is not a DELETE — stopping a run, saving a setting — runs without one; the registry, not the policy, bounds what such a click reaches. The report endpoint is public, so anyone who can reach the hub can send a report and the counter counts what senders say; the log line and the telemetry row come from budgets that keep anonymous senders apart from signed-in ones, small enough that a flood cannot turn the telemetry table over (`TestCSPReportBudgetsAnonymousSendersApart`) |
| **E**levation of privilege | DNS rebinding: a page on a name the attacker controls re-points it at a hub without sign-in on 127.0.0.1, becomes same-origin with it, and reads and drives every API | On a hub with neither SSO nor a static token, a `Host` (or trusted `X-Forwarded-Host`) that is not `localhost`, `*.localhost`, an IP address, `ui.external_url`'s host, a cluster member's advertise host or in `ui.allowed_hosts` is refused with 421 `MISDIRECTED_REQUEST` for reads and writes alike, before anything acts on the request; the probes answer any name (`TestDNSRebindingIsRefusedOnAnOpenHub`, `TestHostAllowed`, `FuzzHostAllowed`; in a browser, `TestAPageElsewhereCannotDriveAnOpenHubInBrowser`). Audited as [`request.host_refused`](../reference/audit-events.md#request). `cloop serve` without a token does the same (`TestServeWithoutATokenRefusesARebindingHost`) | An IP-literal `Host` is admitted: rebinding needs a name, and a browser sends an address only to a page whose own origin is that address. A proxy in front that rewrites `Host` and does not send `X-Forwarded-Host` hides the browser's name from the hub. A hub with sign-in does not check, by design: a rebound name carries none of its credentials |
| **T**ampering | Clickjacking through the documents the silent renewal frames | Only `/auth/renew` and the OIDC callback are framable, by `frame-ancestors 'self'` and `SAMEORIGIN`; everything else is `'none'`/`DENY`; neither framable document holds a control (`TestOnlyTheRenewalDocumentsAreFramable`) | A script injected *into* the dashboard could frame them — it could also call the API directly, so this widens nothing such a script did not already have |
| **S**poofing | A browser signed into another account at the identity provider renews somebody's session as that account | The renewal's pending login records the session's subject from a cookie-bearing request; an `id_token` for anyone else is applied to nothing and audited as [`session.renewal_mismatch`](../reference/audit-events.md#session) (`TestSilentRenewRefusesADifferentSubject`) | The session's claims stay stale until its user signs in again; a user who really switched accounts sees the sign-in banner |
| **I**nformation disclosure | A page elsewhere reads the renewal's verdict | The verdict rides in the result document as data and the sign-in script posts it to `"/"`, the sending document's own origin, so only a same-origin parent receives it; the dashboard also checks the source frame and origin (`TestRenewDocumentPostsOnlyToItsOwnOrigin`) | — |
| **T**ampering | The public login route used as an open redirector via `return` | `safeReturnPath` keeps only a single-slash path on this origin with no scheme, authority, backslash prefix or control character, and the landing page carries it only in HTML attributes, escaped, for the sign-in script to read (`TestSafeReturnPath`, `TestLoginRefusesAnOffSiteReturn`, `TestLoginLandingEscapesDestination`) | — |
| **D**enial of service | A hub whose cookie the browser refuses bounces a lapsed session between itself and the provider | An automatic sign-in that comes back without a live session is not repeated; the banner explains and leaves the choice to the user (`TestDashboard_UnauthorizedPicksTheRightSignIn`) | — |
| **T**ampering | Downgrade or MITM on the wire | TLS 1.2 minimum, ECDHE+AEAD suites only, server cipher preference; `Strict-Transport-Security: max-age=31536000; includeSubDomains` on every response the hub knows arrived over TLS — its own listener, or `X-Forwarded-Proto: https` from a loopback proxy or one in `ui.trusted_proxies` — and on every response of a hub whose public URL (`ui.external_url`, else the SSO callback) is https (`TestSecurityHeadersHSTS`, `TestRequestIsTLS`) | No `preload`, so a browser's first plaintext visit is unprotected. Behind a terminator on another host with neither an https public URL nor a `ui.trusted_proxies` entry the hub sends no HSTS: set one, or set the header at the proxy. A plaintext deployment never gets it, by design |
| **S**poofing | A client names the scheme, host or address the hub believes — choosing the origin its request is judged against, or a fresh address for the sign-in lockout and the rate limiter | `X-Forwarded-Proto`, `X-Forwarded-Host` and `X-Forwarded-For` are believed only from loopback, `ui.trusted_proxies` and signed cluster forwards; `X-Forwarded-For` is walked from the right past trusted proxies, so the leftmost entries a client sent through `$proxy_add_x_forwarded_for` are never read (`TestForwardedHeadersFromAnUntrustedPeerAreIgnored`, `TestClientIPWalksForwardedForFromTheRight`, `TestViewOfIgnoresForwardedHeadersFromUntrustedPeers`); the session cookie's `Secure` follows the same rule (`TestSessionCookieBelievesOnlyATrustedProxy`), and a cluster forward carries the browser's scheme and host on the signed hop (`TestForwardAsCarriesTheBrowsersSchemeAndHost`) | A prefix in `ui.trusted_proxies` is trusted whole: every peer in it can claim any scheme, host and client address. List the proxies, not their subnet, where you can |
| **R**epudiation | User denies making a privileged change | Every privileged allow *and* deny is written to a SHA-256 hash-chained audit trail with actor identity. An append that fails — locked, read-only, full — is counted inside the append path, where no caller can skip it, and recorded in its own chain as an [`audit.gap`](../reference/audit-events.md#audit) row once the database takes writes, so `cloop hub audit verify` tells intact (exit 0) from intact with recorded gaps (exit 3) from broken (exit 2) (`TestAuditAppendFailureIsCountedAndRecordedOnRecovery`, `TestEveryRepeatedAuditFailureIsCounted`, `TestAuditGapFailureDoesNotRecurse`, `TestHubAuditVerifyExitCodes`). Deleting the newest rows is caught by head checkpoints: every 5 min and at clean shutdown the cluster leader writes each chain's newest id and hash to a file outside `.cloop/` and/or a stderr line, sealed under a key derived from `CLOOP_SECRET_KEY` that nothing in `state.db` can produce, once per window across a leader change (`TestAuditCheckpointsOnePerChainPerWindow`, `TestAuditCheckpointWindowClaims`); `cloop hub audit verify --checkpoints` names a tail truncated after a checkpointed id, a database restored from a backup older than a checkpoint, or a re-hashed rewrite, refuses a record whose seal fails, and accepts a prune only when its sealed archive re-hashes into the chain the anchor ends in and holds the checkpointed row — an anchor written over deleted rows, with no archive or a fabricated one, fails, and the hub's own next checkpoint does not vouch for it: it reads each new anchor's archive before its seal says the anchor verified (`TestDeletingTheNewestRowsIsCaught`, `TestAnOlderRestoredBackupIsNamed`, `TestRewrittenHistoryIsCaught`, `TestACheckpointWithABadSealIsRefused`, `TestAPruneBelowACheckpointIsNotTruncation`, `TestAForgedPruneIsNotAccepted`, `TestHubAuditVerifyAgainstCheckpoints`). Gap rows keep their counts through redaction, and a hub adopts a dead process's losses once, whatever its PID or host (`TestAuditGapCountsSurviveRedaction`, `TestAuditFailureStatusLivenessAndDedup`). A restore is told from a truncation by a restore record `cloop db restore` seals under the checkpoint key — derived from `CLOOP_SECRET_KEY`, which is never stored, so write access to the database or the checkpoint file cannot produce one — pinning the head it restored to and its own `audit.restored` row: verify reports `restored (acknowledged)` with the events lost and exits 0, accounting only for checkpoints sealed before the record (`TestASealedRestoreRecordIsAcknowledged`, `TestATruncationAfterTheRestoreIsNotAcknowledged`), names a restore of an unchecked backup as one nothing vouched for (`TestAnUnvouchedRestoreSaysSo`), and refuses a hand-written, unsigned, edited or future-dated record (`TestAFutureDatedRestoreRecordIsRefused`), explains nothing with one sealed under another key, and fails one whose heads the chain no longer holds (`TestAHandWrittenRestoreRecordIsRefused`, `TestARestoreRecordCountsOnlyUnderTheVerifiersKey`, `TestARestoreRecordTheChainNoLongerHoldsFails`, `TestDisasterRecoveryDrill`). The content leaves the box as it is written: the cluster leader forwards every row of every chain — the control plane's and each registered project's — to the sinks in `audit.forward` (syslog over TLS in RFC 5425 framing, HTTPS NDJSON or Splunk HEC, or a file outside `.cloop/`), each record carrying `prev_hash` and `row_hash` so the receiver verifies the chain it holds (`TestForwardsEveryChainToTLSSyslogAndHTTPS`, `TestSplunkHECSink`); a per-sink, per-chain cursor in the control plane advances only after the sink acknowledges, by compare-and-swap, so a leader killed mid-batch leaves its successor to resend from the cursor — no gap, the repeats identified by `row_hash` — and a cluster sends each row once per sink (`TestALeaderKilledMidBatchIsResumedFromTheCursor`, `TestAuditForwardResumesFromTheCursorWhenTheLeaderDies`, `TestAuditForwardRunsOnTheClusterLeaderAlone`); a sink that is down costs no audit append anything and catches up from the database in bounded memory (`TestSinkDownCatchesUpALargeBacklogInBoundedMemory`); rows deleted after they were forwarded are still at the sink while `verify --checkpoints` names the truncation, and a tail truncated and written past, or rewritten, arrives as a fork beside the original, while rows missing inside the chain are recorded as an `audit.forward.discontinuity` row wherever they fall (`TestRowsDeletedAfterForwardingStayAtTheSinkAndCheckpointsCatchIt`, `TestATruncatedTailWrittenPastArrivesAsAFork`, `TestARewrittenChainIsResentAsAFork`, `TestAGapInsideABatchIsRecorded`); retention stops at the slowest sink's cursor unless forced, on every chain from the moment a sink is configured and whatever path names the database (`TestAPruneRefusesToPassAnUnacknowledgedCursor`, `TestHubAuditPruneStopsAtTheSlowestSink`, `TestASinkDownFromTheStartHoldsEveryChain`, `TestTheRetentionHoldMatchesTheFileNotItsSpelling`); sink credentials are named secrets, plaintext off the host is refused at load and at the dial, and the client follows no redirect and never connects to a cloud metadata service (`TestAPlaintextNonLoopbackSinkIsRefusedAtLoad`, `TestTheDialerRefusesMetadataAndPlaintextOffHost`, `TestTheHTTPSSinkFollowsNoRedirect`); a change of sinks is recorded however it was made (`TestAConfigurationChangeIsRecorded`) | Checkpoints pin a chain's length, not its content: an archive the hub verified and somebody later deleted leaves its prune accepted as unverified, so keep `audit.export_dir` where the database's attacker cannot delete. They cannot stop records being deleted from wherever they are kept — keep the file off the box or ship the stderr copy; `cloop hub doctor` warns when the newest is stale or when there is no file. Without `CLOOP_SECRET_KEY` they are unsigned, and the doctor says so. A truncation with nothing written since reads the same as a restore with nothing written since, and the finding says both — a restore done by copying files rather than through `cloop db restore` leaves no restore record, and fails as either. A restore record is believed for what it says about the window lost: whoever holds `CLOOP_SECRET_KEY` can seal one, so the key's holder can explain away a truncation they made themselves. Losses still in a process's memory when it dies are recorded only if its status file survives and a hub starts in that directory again; a `cloop run` or CLI process keeps none, so its unrecorded losses reach only stderr. Forwarding is configured, not default: a hub with no `audit.forward` sinks keeps the content only in `state.db`, and `cloop hub doctor` warns. Rows written in the seconds between a sink's last acknowledged batch and a deletion reach it only if they were sent first. A syslog sink's acknowledgement is its receiver's TCP stack — RFC 5425 has none of its own — so a receiver that crashes holding acknowledged bytes loses them; the https sink's comes from the collector. A forced prune, or a configuration that removes a sink, stops that sink receiving what it had not acknowledged — recorded as an `audit.forward.discontinuity` or `audit.forward.configured` row the remaining sinks receive, which an operator with write access to both the configuration and every sink can still suppress. CEF records truncate payloads, so a chain is verifiable from them by its links only; send JSON where the receiver must re-hash rows ([runbook](../operations/runbook.md#forwarding-the-trail-off-the-box)) |
| **I**nformation disclosure | Dashboard leaks another tenant's project | Every route declares a `Scope`; project-scoped routes resolve the project and re-check visibility (`requireVisibleProject`) | Scoping is per-route; a new route that forgets `Scope` is caught by `routeSpec.validate()` only for the *permission*, not for the scope. **Push channels are not routes at all** — see [scope is not permission](#scope-is-not-permission) |
| **I**nformation disclosure | Live harness output crosses a project boundary | Every log chunk is fanned out with `broadcastToProject`; the replay buffer is keyed by resolved `workDir` and reachable only through accessors that take one (`TestLiveLogDoesNotCrossProjectsOverWebSocket`, `TestLiveLogBufferIsUnreachableWithoutAWorkDir`) | Output is redacted of the values a lease delivered, not of a credential the workload obtained another way — that one lands in its *own* project's buffer, where anyone who can see that project can read it ([what is scrubbed where](model.md#what-is-scrubbed-where)) |
| **I**nformation disclosure | Secrets rendered into the UI or an error | Broker never returns plaintext outside a `Material`; error paths and audit rows are redacted, and the broker, the provider-call audit and browser telemetry recognise credentials from one shared registry (`TestBrokeredMaterialIsNeverDisclosed`, `TestBrokerErrorsDoNotEchoCredentials`, `TestEveryScannerCoversEveryCredential`) | Task **output** is redacted of leased values only — a workload that echoes a token it got elsewhere puts it on the dashboard, and `cloop audit` reports its shape afterwards; a credential shape the registry does not know passes every scanner |
| **I**nformation disclosure / **E**levation of privilege | Approval notifications (Task 20427): a message leaks who asked for which credential, or the hub is made to POST where it should not — the cloud metadata service, an admin port on loopback, a service on the internal network — through a webhook URL, a DNS answer or a redirect | Only an administrator configures webhooks (`user.manage`), and each change is a [`notifications.config.updated`](../reference/audit-events.md#notifications) row naming each webhook by host. A message carries identities, the credential's name and kind, the subject, the deadline and a dashboard link — no justification, decision note or allowlist — and every string is scrubbed of credential shapes (`TestRenderedMessagesCarryNoSecretMaterial`). The sender posts https only, follows no redirect, uses no proxy from the environment, bounds time and body, and checks the address it connects to after DNS: never a cloud metadata service, and a private or loopback address only where the webhook's own `allow_addresses` names it (`TestClientRefusesCloudMetadataEvenWhenAllowed`, `TestClientRefusesNonPublicAddressesUnlessAllowed`, `TestClientNeverFollowsARedirect`). Between a claim and its replacement starting — up to five minutes when the replacement is started by another hub member — the project counts as running, so nobody starts a second run beside one that is about to begin |
| **E**levation of privilege | Project names a malicious or unsigned image for a device's container, or a virtual executor's | Nothing on a device applies the image policy, so the hub does before it dispatches (Task 20424): the allowlists and the digest rule, and under `require_signature` it resolves a tag at its registry, verifies that digest with cosign and dispatches the digest — the device's engine never pulls, so it runs those bytes or refuses. | **E**levation of privilege | A suspect device keeps its credentials after it is taken out of rotation, or a revoked agent keeps its live connection | A cordon or drain — from the dashboard, or from the CLI since Task 20424 — takes back every lease the device's session lists and every lease recorded as issued to it; revoking an agent scrubs its leases and then drops its connection on the member holding it, and every member forgets it. | **E**levation of privilege | Agent requests credentials beyond its grants | Leases are computed hub-side from grants matching (executor, project); the agent's request cannot widen them | A compromised agent gets everything granted to it — which is the argument for narrow, short-TTL grants |

Root on the device can still roll back, by design. | **T**ampering | Release assets replaced so an edge device installs another commit's genuine build | The signed manifest names its commit, every archive must hash to what it lists, and the installed binary must report the manifest's version (`TestStageEdgeRefusesAManifestForAnotherCommit`, `TestStageEdgeRefusesASwappedArchive`, `TestExpectVersionBindsTheBinaryToItsSignature`) | Withholding a build is still possible: an attacker who can delete assets makes an upgrade fail, and the dialog then says the build is not published |
| **E**levation of privilege | A workload running as the agent's user uses the remote-upgrade helper to gain root | The helper is root, but what it accepts is what the hub's frame carries — version, force, settle, reason; it takes the channel from systemd's view of the unit, opens the request without following symlinks, bounds it, deletes it first, ignores it when stale and quotes it in its journal only with control characters removed (`TestApplyUpgradeRequestUsesTheDevicesChannel`, `TestUpgradeRequestRoundTrip`, `TestUpgradeRequestCannotForgeJournalLines`) | Such a workload can ask for anything the hub could, and can trigger restarts by filing requests repeatedly; a request for a build earlier on `main` than the installed one — forced or not — is refused (previous row), except on a device whose installed build predates the sequence |

## Cross-cutting: on-prem hardware through a device forwarder

A [device forwarder](../guides/device-forwarders.md) is a minimal process on
an on-prem machine that carries one USB device or one network segment to the
hub over an outbound tunnel (Task 20429). A binding gives it to one project's
runs (Task 20430): at dispatch the hub relays the forwarder's stream to the
executor that starts the run's sandbox — over the agent's own tunnel to an
executor agent, or into its own process for a container on its host — and that
executor attaches the device and gives it to the sandbox alone. The asset is
the hardware: a hardware security module, a board under test, a seat on a lab
segment.

| STRIDE | Threat | Mitigation | Residual risk |
| --- | --- | --- | --- |
| **S**poofing | A rogue process enrols as a forwarder, or a forwarder claims to carry another device | Single-use, TTL-bounded enrollment tokens with their own prefixes and tables, so a forwarder credential never authenticates as an executor; only hashes are stored; the device chosen at enrollment is authoritative and the hello's claim is ignored | The enrollment token is a bearer secret in transit to the on-prem machine, as an agent's is |
| **S**poofing | A compromised hub, or a peer of the forwarder, asks it for a device it was not configured for | The forwarder answers the USB/IP opening itself and refuses any bus id but the one it carries; it never forwards a device that is itself imported over USB/IP (`TestParseUSBIPRequest`, `TestForwarderNeverCarriesAnImportedDevice`) | A compromised hub reaches the one configured device, which is what the forwarder exists to offer |
| **I**nformation disclosure | Any process on a consuming host reaches the device — before Task 20430 the hub opened an unauthenticated loopback import endpoint any process on the hub host, a host-process run among them, could import from | There is no listener anywhere: the executor that runs the sandbox speaks the USB/IP client handshake itself and hands vhci_hcd one end of a socketpair, or bridges a TAP; the device is attached only for a run of a bound project and given only to its container sandbox — a host-process run, a host-mode agent and a kernel-isolated runtime are refused (`TestForwardedDeviceOnlyReachesASandbox`, `TestHostModeExecutorIsRefusedForwardedDevices`, `TestForwardedDevices`) | While attached, the usbfs node exists on the executor's host, where root can open it; the agent attaching USB runs as root, or with write access to vhci_hcd's attach file |
| **I**nformation disclosure | A project that holds no binding gets the device | The dispatch reads the bindings in force for the run's project — and, for one narrowed to a virtual executor, only on that executor — and opens nothing otherwise (`TestUnboundProjectGetsNoForwardedDevices`) | — |

## Cross-cutting: the sandbox's network position

The hub's reachability into private networks is on the asset list at the top of
this document, and until recently the only thing guarding it was an HTTP proxy.
That was honest but narrow: `pkg/egressbroker` checks hosts, ports, methods,
quotas and the SSRF block set beautifully, and it only ever sees traffic a
workload chose to send it. **A harness that opened a raw socket, ran
`curl --noproxy '*'`, resolved over DoH or spoke anything that was not HTTP
walked past every one of those checks** — not around them, past them; the
allowlist was never consulted. Both drivers said as much in their own comments
(*"it does not filter egress"*), and both left the sandbox with unrestricted
outbound access the moment an operator turned the network on. Given the
standing assumption above — the workload is an LLM running attacker-influenced
code out of a git repository — this was the widest gap in the model.

What binds it now is a filter at the IP layer, compiled from the same
authorisation by `pkg/netfilter` and enforced by the kernel or the CNI rather
than by the workload's cooperation. What it cannot do is enforce a *hostname*
allowlist, and that limit is structural.

| STRIDE | Threat | Mitigation | Residual risk |
| --- | --- | --- | --- |
| **I**nformation disclosure / **E**levation of privilege | A compromised harness exfiltrates data or moves laterally, ignoring `$HTTP_PROXY` | An IP-layer filter compiled by `pkg/netfilter` from the same authorisation the proxy enforces, installed as nftables on the sandbox bridge or as a per-Pod `NetworkPolicy`. Default deny, no configurable default verdict, `ProtoAny` on every drop so ICMP and SCTP are covered, silent drops so a probe learns nothing (`TestNoCompiledPolicyReachesBlockedSpaceByAccident`) | It binds *addresses*. A host allowlist becomes "every public address on these ports" — see the row below. And it is **off unless configured** |
| **E**levation of privilege | A host allowlist is relied on for a workload that dials directly | The widening is opt-in (`allow_public_internet`), never inferred from the presence of host patterns, and every rendering of the policy carries a warning naming the patterns and what they became — an nft comment, a `NetworkPolicy` annotation, an `egress-scope` preflight finding | **Unfixable at layer 3.** `*.github.com` is a name and a packet carries an address. | **E**levation of privilege | A sandbox reaches a cloud metadata service | The metadata services are one table (`pkg/cloudmeta`), read by the proxy, the packet filter and the `NetworkPolicy` compiler alike: `169.254.169.254` and the other clouds' endpoints, including AWS's IPv6 `fd00:ec2::254` inside ULA space and Alibaba Cloud's `100.100.100.200` inside CGNAT space. ## Scope is not permission

The row above says a new route that forgets `Scope` is caught only for its
permission. A cross-tenant log leak in the WebSocket hub showed that the gap is
wider than "routes": **the push channels are not routes**, so no amount of
route-table validation reaches them.

The two controls answer different questions, and passing one says nothing about
the other:

| | Question | Enforced by | Failure looks like |
| --- | --- | --- | --- |
| **Permission** | *May this actor read this kind of thing?* | `Perm` on the route, `gate()` / `require()` | 403 for someone who should have been allowed, or a viewer performing an operator action |
| **Scope** | *Whose data is this, and is this actor one of them?* | `Scope` on the route, `resolveWorkDir` + `requireVisibleProject`, and on push channels `broadcastToProject` | A correctly-authenticated, correctly-authorised operator is shown **another tenant's** data |

A scope failure is the more dangerous of the two because everything about it
looks healthy. The recipient is signed in. Their role permits reading live
output. The audit trail records no denial, because nothing was denied. Only the
*subject* of the data is wrong — and the disclosed party performed no action
and sees no trace.

The concrete bug (Task 20189): `broadcastLog` wrote each chunk of live harness
output to every SSE client and then iterated **all** of `s.hubClients`, which is
`map[workDir]map[*hubClient]struct{}` — a per-project room map, walked as if it
were one flat set. The correct primitive, `broadcastToProject`, already existed
and was already used correctly one function away by `broadcastStateDiff`. Under
it sat a deeper problem: the replay buffer was a single global `[]string` on
`Server`, so the three replay sites (WebSocket connect, SSE connect,
`GET /api/livelog`) *could not* have been correct — `handleLiveLog` even
resolved a `workDir` and then used it only for a liveness probe. There was one
buffer, so there was nothing to be right about.

Three things this generalises to:

1. **Scope is a property of the data, not of the request.** The route table
   checks the request. A broadcast has no request — by the time a chunk is
   fanned out, the identity that caused it is gone and the identities receiving
   it were established on other connections entirely. Anything that fans out
   has to carry its subject with it.
2. **Prefer making the mistake unsayable to auditing for it.** The fix was not
   a `workDir` check bolted onto each read site; it was deleting the global
   buffer. Live output now lives in a map reachable only through accessors that
   take a `workDir` first, so a handler that has not resolved a project cannot
   name a room, and `TestLiveLogBufferIsUnreachableWithoutAWorkDir` fails the
   build if a future edit reintroduces either the direct map access or an
   unkeyed field on `Server`.
3. **"Global" is a legitimate scope — state it, don't default into it.** Three
   other unscoped `s.hubClients` walks were audited in the same pass and left
   alone: `broadcastAuditAppend`, `broadcastExecutorUpdate`,
   `broadcastSecretsUpdate`. The audit trail, the executor fleet and the secret
   inventory are hub-wide resources; there is no owning project to key them on.
   Their reach *is* wider than the permission to read the underlying rows,
   which is exactly why each envelope carries only an event verb and an opaque
   id, and clients re-read the RBAC-gated endpoint for anything more. That
   trade is now written at each call site so the next reader can tell a
   deliberate global from an overlooked one.

### The same class on the subscription path (Task 20197)

Task 20189 made every *broadcast* carry its subject. What it did not reach is
how a stream acquires a subject in the first place, and two of those were
wrong:

- **The connect burst read the wrong project.** `handleEvents` resolved the
  stream's project into `c.workDir`, then built its opening state frame from
  `s.WorkDir`. Every SSE client's first frame was the primary project's full
  task list regardless of the `?project_idx` it asked for — deterministic, not
  a race, on any network where a proxy blocks WebSocket upgrades. The live-log
  replay eight lines below it is the site Task 20189 fixed; the snapshot above
  it was missed.
- **An index-less stream defaulted into a project.** `resolveWorkDir` falls
  back to `s.WorkDir` when no `?project_idx` is given, which is right for a
  request and wrong for a subscription. The dashboard's projects landing page
  holds a stream while no project is selected, so it was subscribed to the
  primary project and primed with its state, live log and run flag — a project
  the viewer may hold no claim to. Those frames were then still arriving when
  the user clicked into a different project, and the client rendered them,
  which is the user-visible bug this task was filed for: *another project's
  tasks on the tasks page.*

Both are point 3 restated from the other side. "No project selected" is a
legitimate scope; defaulting it into "the primary project" is the same
overlooked-global mistake, and it is now stated instead: the client sends
`?scope=global`, the server puts that stream in a room no `broadcastToProject`
call can name, and it is primed with nothing.

The client half is worth recording separately, because it is the part a
server-side rule cannot enforce. A frame carries no project id — the identity
lives in the subscription — so a frame is only interpretable together with the
stream that delivered it. `close()` on a WebSocket starts a handshake and
returns; frames already in flight still arrive. The receiver therefore has to
freeze the scope at the moment it opens the stream and check it on delivery,
which is what `_scopeAccepts` in `04-realtime.js` does. The guard it replaced
asked `selectedProjectIdx === null` — *is a project selected*, not *is this
frame for the project that is selected*.

This bug class had been re-fixed seven times (Tasks 150, 152, 163, 168, 8000,
20013, 20018), each time behind a test that greps the front end as text.
Ordering is not a property text can express, so the regression test runs the
real bundle in node against a DOM shim and delivers the frames in the order
that corrupts the view (`pkg/ui/scoping_test.go`,
`pkg/ui/testdata/scoping_scenarios.js`). Five of its seven scenarios fail
against the parent commit.

## Vulnerabilities found while building this

Recorded because a threat model that lists only theoretical threats is less
useful than one that lists the threats that were actually present. All are
fixed and all have a regression test.

**A GitHub grant went to whatever host a project's origin named (Task 20423).** Repository allowlists were matched on owner/name with the host thrown away: `secretbroker.NormalizeRepo` stripped it, `executor.Workspace.RepoPath` returned only the path, and the grant picker, workspace provisioning, the pinned git-proxy session and a feature's push and pull request chose a credential by `AllowsRepo` alone. A project whose origin was `https://attacker.example/acme/tool` matched a grant for `acme/*`, and the token went there — as the fetch's extraHeader, as the proxy session's upstream credential (the token the proxy exists to keep on the hub), and as the feature's push and API token, handed to `featureops` as "explicit" and so past the very guard written against "handing a GitHub credential to whatever server a project's origin happens to name". Separately, a GitHub Enterprise Server App grant was proxied to the constant `https://github.com`, and the sandbox's rewrite and helper matched `github.com` only, so its token was presented to `github.com` whenever a workload cloned a `github.com` URL with the same owner/name. Every path now binds by (host, path) through one helper, refuses a mismatch naming both hosts, and routes each host through the proxy separately (`TestAnOriginOnAnotherHostGetsNoCredential`, `TestTheFeatureTokenIsNeverLeasedForAnotherHost`, `TestAnEnterpriseAppGrantReachesOnlyItsServer`, `FuzzNoCredentialLeavesItsGrantsHost`).

**Kubernetes access failed open in four places (Task 20420).** *A constrained
kubeconfig without the monitor:* with `executors.kube_guard` off the broker
delivered the minimised kubeconfig whatever the grant said, so "read-only,
namespace `app`" handed the workload everything the kubeconfig's identity may
do — the namespace is only `kubectl`'s default and nothing checks verbs — while
`hub doctor` only warned. Such a grant is now refused
(`ErrKubeConstraintsUnenforced`) unless an administrator records an audited
acknowledgement on it, and the doctor fails while an unacknowledged one exists
(`TestConstrainedKubeconfigIsNotDeliveredWithoutTheMonitor`,
`TestKubeGuardDisabledWithAConstrainedKubeconfigGrantFails`); the `kubernetes`
executor's own cluster credential, used in the hub and never delivered, is not
(`TestAKubeconfigTheHubKeepsIsNotRefused`). *Credentials
minted around the monitor:* it refused `serviceaccounts/token` and read no
request body, so a write grant — `edit` may create Secrets, Pods and
Deployments — could create a `kubernetes.io/service-account-token` Secret, or a
workload running as another ServiceAccount, and hold a non-expiring credential
that never passes the monitor and survives a revoke. The monitor now reads
create, update and patch bodies of Secrets, workloads and custom resources —
any group the API server does not serve itself, `*.k8s.io` ones included;
every occurrence of a repeated key, and the stored object before a patch —
refuses an encoding it cannot read, and refuses token Secrets, non-default
ServiceAccounts, node access, RBAC writes, CertificateSigningRequests and
`ephemeralcontainers`, each under its own reason (`TestCredentialWritesNeverReachTheCluster`,
`TestAPatchIsJudgedAgainstWhatItPatches`; on kind, `tests/kube` P8–P14). *A share's
uploader steering a colleague's revoke and renew:* `cloop remote kube revoke` and
`renew` act with the caller's own cluster credentials on metadata the uploader
wrote — `kube.objects`, `kube.context`, a ServiceAccount from unverified JWT
claims — and deleted every listed object unchecked, before the hub authorised
anything, and renew sent the minted token to whatever server the share named. A
`secret.grant` holder could have an administrator delete
`ClusterRoleBinding/cluster-admin`, or mint a `kube-system` token and send it to
the attacker's server. Now the hub records owner, server, CA, ServiceAccount
(held to the share's own) and objects itself and is asked first; the CLI refuses
a context for another server or CA, deletes only objects read back with the
share's label and owner annotation (by uid and resourceVersion), mints only for
a ServiceAccount read back the same way; and the hub sends a pushed token only
to the server that minted it (`TestRevokeDeletesNothingTheShareDidNotCreate`,
`TestAdoptSendsATokenOnlyToTheServerThatMintedIt`,
`TestRevokeAsksTheHubBeforeTouchingTheCluster`; on kind, the crafted share).
*Renewal for a denied owner:* the hub went on renewing the shares of users
suspended at the identity provider or offboarded under a legal hold; it stops
now and records why (`TestRenewalStopsForADeniedOwner`,
`TestRenewalStopsForAnOwnerTheIdentityProviderDeactivated`).

**A project's name ran as script in an admin's dashboard, and nothing stood in
the way.** The Projects grid, the Overview's project cards, the header's
dropdown and the hidden-projects dialog put a project's name into an inline
handler as `onclick="openProject(3, "…")"`, the name JSON-encoded with its
quotes turned into `&quot;`. JSON does not escape `&`, and the HTML parser
decodes an attribute's character references before the handler is compiled: a
name holding the literal text `&quot;` ended the string, and what followed ran
when the card was clicked. A name is the base name of a directory anyone with
`project.write` creates through `POST /api/projects/new`, a hub admin sees
every project, and the policy allowed it — `script-src` carried
`'unsafe-inline'` because the page was built from 234 inline handlers and ~70
more generated in script — and `el.setAttribute('onerror', …)` carried a
payload past the 255-byte limit on a name. Every handler is now a `data-action`
the bundle's dispatcher routes, the policy runs only the hub's own script
files, and violations are reported to the hub (Task 20408;
`TestDashboard_HostileProjectNamesStayData`,
`TestHostileStrings_EveryControlInBrowser`). The browser sweeps that prove it
found three more on their first runs. Every viewer's presence bar rendered the
other signed-in users' display names as markup — a name is whatever the
identity provider releases, so a user who could set their own put script into
everyone's dashboard who opened the same project; it is escaped now
(`TestHostileMemberIdentities_InBrowser`). A task's links rendered
`href="javascript:…"` from whatever the plan said; they are links only over
http(s) now. And the Assistant's input box threw on every keystroke, because
its inline handler called a function the bundle never exposed.

**Offboarding severed the person and kept their credentials.** `cloop hub user
offboard` and the dashboard's offboarding ended sessions, tokens, glasses links,
memberships, leases and running tasks, and touched none of the per-user stores
added after them. A departed user's personal secrets — GitHub PATs, the
git-proxy-guarded ones included, and kubeconfigs — stayed sealed indefinitely,
with every grant over them live, so a shared project a colleague ran kept
spending them; the runbook's only remedy was for an admin to revoke personal
grants by hand. Their pending grant requests stayed open, approvable into a
grant for somebody the hub no longer admitted. Their Claude Code login home —
the OAuth refresh token in plaintext, the CLI's transcripts and project history
— stayed under the config directory of every hub member that had served them,
and `claudecodeauth.ForgetHome`, documented as the deprovisioning path, had no
caller; a login in flight stayed parked in a member's memory. And deleting a
secret only unlinked its row, leaving the ciphertext and wrapped data key in
the database file's free pages, under a key the hub still holds. Fixed in Task
20400: the run revokes the grants, destroys the secrets through the broker with
their sealed columns overwritten first and a tombstone left to name them,
withdraws the requests, and ends the Claude logins on every member, reporting
each copy it could not reach; `--keep-credentials` keeps the stored credentials
for a legal hold and severs everything else; and a project that lost a
credential is refused it by name (`TestOffboardingLeavesNoPersonalSecretOfTheDepartedOwner`,
`TestOffboardingStoredCredentials`, `TestDeleteBrokerSecretOverwritesTheSealedBytes`,
`TestOffboardReachesEveryMembersClaudeHome`, `TestTheSharedProjectIsToldWhichCredentialItLost`).

**A failed-over run was nobody's run, and the run it replaced kept its
credentials.** When an executor stopped answering, failover started the stranded
run's recorded spec on a replacement and watched only for its session to close.
The spec is stored without the run's leased credentials and project seed, so on
an isolating executor the replacement started with no Claude login and no
project to work on; nothing streamed its output to a dashboard, nothing merged
the result it sent back, and nothing settled the project when it ended. The hub
meanwhile went on following the stranded run, whose driver answered "unknown"
for as long as the device stayed away — so the project showed "running"
indefinitely, and the stranded run's lease keepalive read "unknown" as alive and
went on extending its credentials, git-proxy and Kubernetes-monitor sessions
included. A device that came back resumed the workload beside its replacement.
And placement chose the replacement for health alone, so a run could land on
an executor whose access list excluded the person who started it — or, with
host execution allowed, on the hub's own host: the host driver has no
concurrency limit and so outranked every device on free slots, and a
replacement dispatched as a real run would have run there as a host process.
Fixed in Task 20396: the replacement goes through `startWorkloadAs` pinned to the
placed executor and is followed as the project's run on the member able to reach
it; the stranded run is given up — its leases and egress session closed, its
driver told to abandon it, which a returning device hears as "terminate"; a run
nothing replaced leaves the project paused with an `executor_lost` reason; the
session store's claim overrides a driver that cannot answer; a restricted
executor is never a failover target, and an isolated run never fails over onto
the hub's host (`TestFailedOverRunBecomesTheProjectsRun`,
`TestAbandonedWorkloadIsTerminatedWhenItsDeviceComesBack`,
`TestLostExecutorWithNoReplacementLeavesRunning`,
`TestFailoverNeverMovesARunOntoARestrictedExecutor`,
`TestFailoverNeverBringsAnIsolatedRunOntoTheHost`).

**A workload that took its node down was carried to every node in turn.**
Executor failover moved a session stranded on an unreachable node to the next
healthy one with `Attempt + 1` and no ceiling, and returned its tasks to pending
for the replacement to pick up. A fork bomb, a workload that exhausts memory, or
one that panics the kernel therefore took down the next node, and the next,
until every enrolled device had gone down once — and a person pressing Run
afterwards started the cycle again on the same task. The table above said so
in its own residual-risk column. Fixed in Task 20391 by `executors.failover.max_attempts`,
decided inside the claim's one conditional `UPDATE` so that supervisors and hub
members racing for a session cannot disagree about it, and by quarantining a
task two distinct nodes went down under until an explicit reset
(`TestFailoverCapStopsANodeKillerAtMaxAttempts`, `TestTwoSupervisorsRacingAtTheCap`,
`TestRunPM_RetryFailedLeavesASuspectedNodeKillerFailed`). Building it found a
second, quieter defect: the session watcher's close overwrote whatever state a
failover's claim had recorded once the dead node's stream finally ended, so a
claimed session read as `failed` and its chain disappeared from the record
(`TestCloseLeavesAClaimedSessionAlone`).

**The Projects grid's Run button skipped the executor access list and the
quotas.** `POST /api/run` admits a run through the executor's audience, the
daily budget and a concurrency slot. `POST /api/projects/{idx}/run` — the Run
button on a project card — and a new project's `autoRun` started the same run on
the same executor and checked none of them, so an identity an administrator had
left off a restricted executor's access list was refused on the Overview and
admitted one click away, and a tenant at its concurrency cap could start one
more run there every time. Found re-verifying this document's residual-risk
column in Task 20391, which also gave both paths the same gates
(`TestProjectGridRunHonoursTheExecutorAudience`,
`TestProjectGridRunTakesAConcurrencySlot`,
`TestNewProjectAutorunHonoursTheExecutorAudience`).

**The downgrade guard could not order two builds of `main`, so root would roll a
device back on request.** Since the edge channel (Task 20376) a device follows
the hub's own build: its unprivileged agent files `upgrade-request.json`, and
the root helper installs whatever `edge:<commit>` it names once cosign has
verified it against `edge.yml` on `main`. Every retained edge build passes that
— up to thirty of them — and the guard meant to stop a device moving backwards
compared versions, which for two `dev+g<sha>` builds are "not comparable", so
only the protocol was checked. A compromised agent process, or a compromised hub,
could therefore have root install any older signed build at the same protocol,
including one from before a fix to the helper itself; the request's `force` flag
waved through even a protocol downgrade, so an old release was reachable too. The
signed manifest's `built_at` could not order them either: it is when a build ran,
and a re-run of an old commit is "newer". Fixed in Task 20380 by stamping every
build with its commit's first-parent position on `main` — build scripts, signed
manifest (schema 2) and `cloop version --json` — and refusing in the installer a
staged build earlier than the installed one, read from the binaries themselves,
overridable only by a local root `--force` and never by the request or the hub
(`TestApplyUpgradeRequestCannotForceARollback`,
`TestCheckUpgradeSafetyOrdersBuildsByTheirPlaceOnMain`). The schema-1 manifest
is still published beside schema 2: the code already on devices reads nothing
else, and dropping it would have stranded every one of them off the channel
(`TestTheSchema1ManifestIsWhatAnOlderReaderAccepts`).

**`--cidrs 0.0.0.0/0` waived the entire SSRF block set.** An explicit CIDR is
what waives the block set — that is the design, and it is why there is no
blanket `allow_private` flag and why reaching the metadata service is meant to
be a sentence an operator writes out as `169.254.169.254/32`. A `/0` was that
blanket flag spelled differently: one grant flag turned off cloud metadata,
loopback, and the operator's entire internal network at once. So was any prefix
merely *containing* `169.254.169.254` without naming it — `169.254.0.0/16`
reaches the credentials of the host the hub runs on, which on a cloud instance
is the whole account. Fixed in `egressbroker.validateAllowPrefix`, at grant
time where the operator sees the message, with `pkg/netfilter` refusing the same
shapes so the two layers cannot disagree about it
(`TestWideCIDRsCannotBypassTheBlockSet`,
`TestGrantsThatWouldRemoveTheBlockSetAreRefused`).

**But only the grant layer enforced it, and only for one address.** The
containment rule lived in the broker; the packet filter's own allowlists —
`egress_filter.allow_cidrs`, and the dashboard's device, virtual-executor and
project firewalls — refused a `/0` and nothing else, so `169.254.0.0/16` written
in any of them compiled ahead of the metadata drop and opened the service on its
ports. And the block set named one metadata address. AWS's IPv6 IMDS
(`fd00:ec2::254`) sits inside `fc00::/7` and Alibaba Cloud's (`100.100.100.200`)
inside `100.64.0.0/10`, both ranges a bench host doing hardware or L2 work might
plausibly allow — and allowing one opened a metadata service while the UI called
the range "private". Fixed by moving the services into one table (`pkg/cloudmeta`)
that the proxy, the packet filter and the `NetworkPolicy` compiler all read, and
one containment rule enforced at every surface that writes an allowlist: config
load (so `cloop ui` refuses to start and `cloop hub doctor` fails), the three
firewall APIs and their CLI (400, naming the service and the explicit
alternative), and egress grants. A rule set stored before the rule fails safe —
`Compile` drops the service ahead of any allow that only contains it, the
`NetworkPolicy` gets matching `except` entries, the hub ships device firewalls
with the services denied so an older agent closes them too, and the firewall
cards and the doctor list such stored rules. Proven on a real kernel against the
live Alibaba Cloud metadata endpoint, in a container and in a device sandbox
(`TestNoAllowlistReachesAMetadataServiceByContainingIt`,
`TestAllowListVerdictAgreesAcrossFilterAndBroker`,
`TestIntegration_AContainingAllowKeepsTheMetadataServiceClosed`).

**The host-side ruleset filtered the Internet and left the host open.** The
first version had a `forward` chain and nothing else. But the routing decision
picks the hook: destinations the host forwards on reach the `forward` hook,
while destinations that belong to the host itself — the bridge gateway, any
address bound on any of its interfaces — reach the `input` hook instead. So a
sandbox under a policy that dropped `172.16.0.0/12` could still open a
connection to a service on the host's own `172.x` bridge address, which is
precisely the lateral movement the block set exists to refuse. Found by testing
against a real container, not by reading the rules. Fixed by rendering both
hooks with the same rules, since which hook a destination takes is a fact about
the host's routing table and not a security boundary
(`TestHostSideFilterCoversHostBoundServices`, `TestBridgeFormFiltersBothHooks`).

**Project creation was unconfined, which made project deletion an arbitrary
delete.** `POST /api/projects/new` ran `filepath.Abs` + `os.MkdirAll` on the
caller's string with no confinement at all, so a relative `dir` resolved
against the *hub process's* cwd and escaped through `../../../..`, while an
absolute one simply landed wherever it pointed. On its own that is a
directory-creation nuisance. The chain is what matters: the created path is
registered, and `DELETE /api/projects/{idx}?delete_root=true` then
`os.RemoveAll`s it behind a guard that rejected only `""`, relative paths,
`/` and `$HOME` — `/etc`, `/usr`, `/var` and `/home` all passed as "safe".
Because `MkdirAll` returns nil for a directory that already exists, two
`project.write` calls were an arbitrary-directory-deletion primitive. Fixed by
giving creation and deletion one shared predicate, `isSafeProjectRoot`, which
now also refuses system subtrees and bare top-level directories while leaving
`/var/lib/cloop/projects/…` — where the packaged image puts state — working
(`TestIsSafeProjectRootRejectsSystemPaths`,
`TestProjectCreateRejectsSystemDirectories`).

That predicate was a list of directories nobody should name, and the dangerous
ones were not on it (Task 20418). `dir` — which `cloop remote init --dir` sends
too — was confined by nothing else, and `project.write` sits at maintainer. A
maintainer could register an ancestor of the hub's own directory (`/var/lib` on
the packaged image, whose `WORKDIR` and `HOME` are `/var/lib/cloop`;
`/root/Projects` on a host install) or the projects root itself. On a strict hub
the container driver is the default executor, and it bind-mounted that tree
read-write at `/workspace` with no overlap check, so model-authored code could
read `.cloop/hub.env` (`CLOOP_SECRET_KEY`, `CLOOP_UI_TOKEN`), the control
plane's `state.db` and `projects.json`, and read and write every tenant's
project: a maintainer became an administrator holding every sealed secret.
`?delete_root=true` then removed any registered path the list missed — children
of `/var`, `/srv` and `/opt`, other users' homes — so on a hub running as root a
maintainer could register and delete `/var/lib/postgresql`. The `409` for an
existing project told a caller whether one existed at a path they could not
see; the existence check, the `mkdir` and `cloop init` were not one step, so two
creations of one path both ran init and the loser's executor and grants landed
on the winner's project; and no creation or deletion was audited. Fixed with one
predicate for every way a directory becomes or acts as a project
(`pkg/projectconfine`): creation, the registry write that ends it, operator
`--projects` (flagged, not refused), a project's own state trying to relocate
it, and every dispatch, re-checked before any bind mount or host fork and backed
by the drivers themselves. The path is claimed in the control plane before
anything is made (`project_claims`, migration 0068), refusals that depend on
what exists are answered identically, `?delete_root=true` removes only a
directory the hub made, and `project.create` / `project.delete` are audited. The
hub's background worktree sweep, which every fifteen minutes ran `git` in
repositories a sandbox writes with a bare `exec.Command`, the hub's whole
environment and no deadline, now runs it hardened (`executor.GitEnv` +
`HardenedGitConfig` + `BoundChild`), and the call-graph gate covers the hub's
background entry points as well as its handlers
(`TestBackgroundSweepRunsNoRepositoryProgram`,
`TestBackgroundAnalysisDetectsASeededViolation`). See the row under ③.

**Creating a project where one existed wiped it.** `POST /api/projects/new`
ran `cloop init` in the directory it was given, and `cloop init` overwrites the
state it finds — plan, history, settings. A maintainer who named the path of a
colleague's project, which they could not even see, reset it, and the registry
kept the entry under its owner, so nobody saw who did it; a re-run of `cloop
remote init` would have done the same to the developer's own. Found while adding
that command (Task 20417). Fixed by refusing, with `409 CONFLICT`, any directory
that already holds a project (`TestProjectNewRefusesADirectoryThatHoldsAProject`)
— and since Task 20418 in the same words as every other refusal that depends on
what is on the host, unless the caller can see the project or administers the
hub, so the refusal is no longer a way to learn what exists where.
The same task found the creation request binding an executor without consulting
its access list, which the bind route does: a user kept off a restricted executor
could still create a project pinned to it. The run-time gate refused the run, so
nothing executed there; creation now applies the list too
(`TestProjectNewAppliesTheExecutorsAccessList`).

**A 60-byte read request returned a 109 MB response.** `/api/analytics`
validated that `?from=`/`?to=` *parsed* as dates but never how far apart they
were, and `time.Parse` accepts years 0000–9999. The handler builds one label
per day in the window and sizes a `float64` slice per provider from it, so
`?from=0001-01-01&to=9999-12-31` drove a ~3.65M-iteration loop; measured on an
empty project it returned 109,562,327 bytes in ~2s. The route carries `read`,
the lowest permission on the hub, and the per-IP limiter defaults to 20 rps, so
a viewer — or anyone at all on a hub with auth misconfigured — could OOM the
daemon with a handful of concurrent GETs. Fixed by clamping the window to
`maxAnalyticsWindowDays` and normalising an inverted range, which also keeps
every dataset the same width as the label axis
(`TestAnalyticsBoundsTheDateWindow`, `TestAnalyticsAcceptsOrdinaryWindows`).

**Mutating verbs were served by read-only routes.** Ten routes are registered
without a method prefix, so `http.ServeMux` hands them every verb, and none of
the handlers checked `r.Method`: `DELETE /api/state` returned 200 and the full
state, `DELETE /api/projects` returned 200 and a 37 KB project listing. No data
was destroyed — the handlers only read — but a mutating verb was being
authorized by the `read` permission, and a client that dropped the index from
the real `DELETE /api/projects/{idx}` got a cheerful 200 from a listing instead
of an error. Fixed in `gate()` rather than per-handler, expressed as "a
mutating verb is never authorized by a read permission" so it also holds for
routes added later, and placed ahead of the `authzActiveFor` short-circuit so
it applies in single-tenant deployments too
(`TestReadOnlyRoutesRejectMutatingMethods`).

**Live harness output was broadcast to every project's dashboard.** One
project's raw stdout — file paths, source excerpts, anything the workload
echoed — reached every open dashboard on the hub, including projects belonging
to other identities, and was replayed from a single global buffer to any client
that connected afterwards. See [scope is not permission](#scope-is-not-permission)
for the anatomy; fixed by routing every chunk through `broadcastToProject` and
partitioning the buffer by resolved `workDir`.

**The Groq API key was passed on the argv.** `/api/voice` appended a
caller-supplied `--groq-api-key` to the subprocess argv, where
`/proc/<pid>/cmdline` exposes it to every local user for the lifetime of the
child — the same exposure `install_script.go` already refuses for enrolment
tokens. Fixed by passing it in the environment, which `cloop listen` already
reads as `GROQ_API_KEY`; the plumbing appends to the inherited environment
rather than replacing it, since `applyLease` reads a nil `Spec.Env` as
"inherit `os.Environ()`" — on the host driver. On an isolating executor it no
longer inherits anything; see the next entry.

**The hub's master sealing key was forwarded into every sandbox that held a
grant (Task 20234).** `applyLease` seeded `Spec.Env` from `os.Environ()`
whenever the caller left it nil, which every dispatch from `handleRun` does.
Every name in `Spec.Env` is then forwarded into the workload — the container
driver emits a bare `--env NAME` per entry — so the hub's entire process
environment crossed the isolation boundary into a container running
model-authored code. On a hosted deployment started from `.cloop/hub.env` that
environment contains `CLOOP_SECRET_KEY`, the master key that unseals *every*
credential in the broker, and `CLOOP_UI_TOKEN`, which bypasses RBAC and sees
every project on the hub. A sandbox leased one repository-scoped token was
handed the keys to the store that token came from, which inverts the entire
point of [scoped grants](#cross-cutting-the-secret-and-egress-brokers).

It applied only to a project that *held* a grant, because `applyLease` returns
early on an empty lease — so it was live on exactly the enterprise path and
absent from the one a developer tries first. It was invisible to every existing
test: the container suite asserts credentials never reach the *argv*, which was
true, and nothing asserted what reached the environment.

Fixed by making the inheritance conditional on `executor.IsolatesFromHost`: a
host-executed harness still inherits, because it is a process on this machine
that would have had that environment anyway and needs `PATH` and `HOME`; an
isolated workload gets exactly the leased material layered on its image's own
environment, and anything else it needs is a grant. The same fix removed a
second symptom — the host's `PATH` was replacing the image's inside the
sandbox, so a `sh` that existed at `/bin/sh` could not be found.

Found by building the end-to-end circuit in `tests/flagship`, which is the
first test to run a real task through an isolating executor rather than against
a fake. Guarded by `TestIsolatedExecutorDoesNotInheritTheHubEnvironment`,
`TestHostExecutorStillInheritsTheEnvironment` and
`TestUndeclaredIsolationIsTreatedAsHostExposure`, and end to end by the
flagship circuit, which has the sandbox report whether it can see either
variable and fails if it can.

## Cross-cutting: hub members

Several `cloop ui` processes may serve one control plane as a
[hub cluster](../architecture/hub-cluster.md), forwarding to each other the
requests only one of them can answer. The members trust each other exactly as
much as a single hub trusts itself — they share its database — so what needs a
boundary is the channel between them, which a client can also reach.

| STRIDE | Threat | Mitigation | Residual risk |
| --- | --- | --- | --- |
| **S**poofing | A client poses as a member to skip the per-address rate limit, claim another address in the audit trail, or reach `/api/internal/cluster/*` | Every forwarded request carries an HMAC over the sender, the recipient, a timestamp, a nonce, the method, the URI and the original client's address, keyed by a secret kept in the control-plane database; a request whose claim fails verification is refused with `403`, never served as an ordinary one (`TestForgedAndReplayedPeerClaimsAreRefused`, `TestClusterRefusesForgedPeerClaims`) | Anyone who can read `state.db` holds the key — and could already rewrite every table the hub trusts |
| **S**poofing | A captured forwarded request is replayed | The nonce is single-use at its recipient within the two-minute skew window, and the signature names the recipient, so the capture is refused everywhere else (`TestAPeerRequestIsGoodOnlyAtItsRecipient`) | — |
| **E**levation of privilege | Forwarding launders a request past authorization | The owner re-authenticates the forwarded caller from its own cookie or token and applies the route's permission as if reached directly; a member vouches only for the client's address | — |
| **I**nformation disclosure | Forwarded requests carry session cookies and tokens across the network | Members advertise `https://` URLs where others can observe the traffic, and verify peers against the system roots, their own certificate and `ui.cluster.peer_ca_file` | The default is plain HTTP on loopback, and the Helm chart's is plain HTTP between Pods — safe only because every member is on one node, which a cluster requires anyway |
| **D**enial of service | A member heartbeats but stops answering — a stuck handler, a listener that stopped accepting — so requests forwarded to it hang, and its runs are never adopted because it is not dead | Every member probes its peers over the peer channel; one that fails every probe for the member TTL is treated as down for adoption and forwarding — its runs adopted, nothing forwarded to it, the requests waiting on it failed at once — and an unresponsive leader's adoption is done by the member serving longest (`TestAMemberThatHeartbeatsButDoesNotAnswerIsTreatedAsDown`, `TestAMemberThatStopsAnsweringHasItsRunAdopted`, `TestAnUnresponsiveLeadersRunsAreAdoptedInItsStead`). A forwarded request waits at most 6 minutes for response headers (`TestAHungForwardIsBoundedByTheHeaderTimeout`) | A member that answers probes but hangs one kind of request holds that request's callers for up to the header timeout. A member judged unresponsive wrongly — slow, not stuck — has its runs adopted, and lets them go at its next ownership check |
| **T**ampering | Two members act on one run, or one agent | Runs, agents and in-flight logins are owned through compare-and-swap rows; a start on a project another member runs is refused with `409`; adoption of a dead member's run is conditioned on the row it read | A member paused past its TTL whose run was adopted meanwhile keeps streaming it until its next ownership check — a few seconds after it resumes — then lets it go without settling it |
| **D**enial of service | A member dies holding runs, agents and logins | Survivors adopt runs whose workloads outlived it — taking over their secret leases unless they were revoked meanwhile, and restoring the git-proxy, Kubernetes-monitor and egress sessions those feed (`TestAdoptedRunTakesOverItsLease`, `TestAdoptedRunsSessionsAreRestored`) — agents reconnect to them, and a new leader takes the exactly-once duties. A run whose executor a failover claimed is not adopted, and a failed-over run's replacement is started and followed by the member holding its agent, which takes the run's owner row; the member that followed the stranded run is told on the bus and, should that message be lost, finds the claim in the session store on its own sweep (`TestFailedOverRunIsFollowedByTheMemberHoldingItsReplacement`). No run goes unsupervised (Task 20419): a dispatch is recorded as an intent before its workload exists, a dispatch whose intent, session or run record cannot be written is refused and its workload stopped (`TestADispatchThatCannotBeRecordedIsRefused`, `TestADispatchWhoseIntentCannotBeRecordedNeverStarts`), and a member that died between starting a workload and recording its run has that workload stopped and its credentials taken back before its claim is cleared (`TestADeadMembersUnrecordedDispatchIsReaped`). An adopted workload's row names its adopter, so a member started later does not adopt it a second time (`TestAWorkloadRowIsAdoptedByOneMember`, `TestAClaimedRowIsAdoptedOnce`), and its staging directory and lease Secret keys come with it, so its wipe, revocation and App token refresh do too (`TestAnAdoptedContainersFileIsRefreshed`, `TestRefreshReachesAnAdoptedPodsLeaseSecret`) | In-flight logins of the dead member are lost. A host-executor run survives a killed member only on its host, without its credentials, and with no output a survivor can stream. Its proxy sessions come back only with what they stand on — an adopted run's, a device workspace's pinned session (`TestAWorkspaceSessionSurvivesARestart`), a CI relay session at the job's next call (`TestCI_SessionSurvivesAHubRestart`); a Kubernetes Pod's workspace session and any unrecorded session are lost, and a restored egress session is served only by the adopter's own listener. Rate limits and connection caps are per member, so N members admit N times the per-address rate |

## Cross-cutting: SCIM provisioning

The identity provider provisions the hub at `/scim/v2` (Task 20415,
[guide](../guides/scim-provisioning.md)) with a credential minted on the hub.
That credential carries the provider's authority over the people it
provisions: deactivating one suspends them, deleting one offboards them, and
membership of a provisioned group is a claim role bindings can name. So the
threats are less about the protocol than about who else could hold that
authority.

| STRIDE | Threat | Mitigation | Residual risk |
| --- | --- | --- | --- |
| **S**poofing | The SCIM credential is presented as an API token, on the dashboard, or in a query string, or an API token or session cookie is presented to `/scim/v2` | The credential is accepted on the `/scim/v2` routes only, and only from the `Authorization` header; anything else there is refused with 401 and a bounded `scim.request_refused` row (`TestSCIM_TheCredentialOpensSCIMAndNothingElse`). The routes are public to the hub's own authentication precisely so that no session or token reaches the SCIM handlers | — |
| **S**poofing | The credential is guessed, or read from the database or a backup | 256 random bits behind a 64-bit id; stored as an HMAC (`apitoken.DeriveHash`) and verified before anything else is asked, in constant time — an id that does not exist is compared against a stand-in, so it answers in a wrong secret's time; a wrong one counts against a lockout of SCIM's own (next row); the format is in the shared redaction registry (`cloop-scim-credential`), so it is scrubbed from logs and audit rows | A copy taken from the identity provider's configuration — or from Terraform state, where the module keeps it — is the credential. Every request is verified, so the lockout changes what a guess is answered, not how many are tried: the per-address request rate limit bounds those, and 256 bits are not guessed |
| **D**enial of service | Provisioning — and every suspension the provider sends — is locked out by somebody else's failures: five wrong credentials a minute from the provider's shared egress address, or from any address behind a proxy not in `ui.trusted_proxies` (where every caller shares the proxy's), and SCIM answered the provider's valid credential `429` before it verified it; static-token and API-token failures from that address counted toward the same lockout (Task 20422) | The credential is verified first and a valid one is served whatever its address's lockout says; only failures are counted, in SCIM's own per-address bucket — five a minute, then `429` with `Retry-After` for a minute, audited as `scim.request_refused` `locked_out` — kept apart from the dashboard's sign-in lockout in both directions (`TestSCIM_ALockedOutAddressStillAdmitsTheProvider`, `TestSCIM_FailuresKeepTheirOwnBucket`). A credential store that cannot be read is answered `503`, which the provider retries, and counts against nobody | Callers sharing an address still share its SCIM bucket, so one guesser's lockout answers another guesser `429` — never a valid credential. The per-credential rate limit (below) is spent by whoever holds the credential, provider or thief |
| **E**levation of privilege | A leaked credential promotes someone: it adds an identity to a provisioned group that a `scim_group` binding makes admin | Provisioned groups grant nothing until an administrator binds one; minting a credential needs `user.manage`; every membership change is audited under `scim:<name>` (`scim.group_members`); revoking the credential is immediate | A credential is as strong as the strongest role a `scim_group` binding grants. Bind admin on app roles at the provider, not on a provisioned group, where that is unacceptable |
| **D**enial of service / **T**ampering | A leaked credential suspends or offboards people: it deactivates provisioned users, or provisions a user whose match value is someone the provider never sent and deletes it, which runs the full offboarding — destroying that person's stored credentials | Per-credential rate limit (`rate_limit_per_minute`, `TestSCIM_EachCredentialIsRateLimited`); every change audited under `scim:<name>`; a [legal hold](../guides/scim-provisioning.md#legal-holds) keeps stored credentials through any offboarding (`TestDeleteRunsTheFullOffboardingUnderAHold`); revocation is immediate | This is the provider's authority, and the hub cannot tell the provider from a thief holding its credential. A suspension is undone by reactivating; what an offboarding destroyed is not. Alert on `scim.user_delete` and `scim.user_suspend` bursts |
| **E**levation of privilege | The provider's reactivation lifts a deny an administrator wrote, or an offboarding's | A reactivation removes only the deny rows its own suspension wrote — same id, reason and author — and resumes only the grants it suspended (`TestReactivationLiftsOnlyWhatTheSuspensionWrote`, `TestADenyRewrittenDuringSuspensionIsKept`); after an offboarding nothing is lifted (`TestOffboardAfterDays`) | — |
| **S**poofing | A provisioned user is matched to the wrong person, so a deactivation suspends a bystander or misses the leaver | Matching is on one configured claim; a value two identities carry is refused a guess — the value alone is denied and neither identity is granted the user's groups (`TestAmbiguousMatchesAreRefused`); a user with no value, or under `oid` an `externalId` that is no object ID, is counted unmatchable and reported by `cloop hub doctor` (`TestAnExternalIdThatIsNoObjectIDIsUnmatchable`) | Matching on a reusable value (`email`, `preferred_username`) denies whoever is given a departed person's address next, until the old provisioned user is deleted — fail-closed, but a support ticket. `oid` and `sub` are never reused |
| **E**levation of privilege | A client asserts provisioned groups itself — in a token, a header, a forged subject | Provisioned groups come from the hub's own directory at every decision; any the caller's subject carries are discarded (`TestASubjectCannotAssertProvisionedGroups`, `TestProvisionedGroupsComeFromTheDirectoryAtEveryDecision`) | — |
| **R**epudiation | Who suspended, offboarded or regrouped this person | Every change is a control-plane audit row under `scim:<credential name>`, the suspension with the counts of what it ended; refusals are recorded, bounded per minute | The provider's own provisioning logs say which administrator caused the change; the hub knows only the credential |
| **D**enial of service | Oversized or pathological requests: a deep filter, a huge PATCH, a page of everything | Bodies are capped at 1 MiB and must be JSON or `application/scim+json`; filters at 4096 bytes and 32 levels; PATCH at 1000 operations; pages at 200 (`TestFilterRefusesWhatItCannotRead`, `TestPatchRefusals`, `TestParsePage`) | — |
| **I**nformation disclosure | `/scim/v2` reveals what the hub knows about people | It returns what the provider sent and nothing the hub derived — no sessions, tokens or roles; a password a provider sends is discarded and never stored or returned | Whoever holds the credential reads the provisioned directory: names, addresses, managers, groups |

The plaintext key goes only to the configured KMS: no plugin socket in a directory every user shares, no plain HTTP off loopback, no redirect carrying the Vault token elsewhere (`TestKMSv2RefusesASocketAnyoneCouldHaveBound`, `TestTransitRefusesPlaintextOffTheHost`, `TestTransitRefusesARedirectToAnotherServer`). Every call is measured (`cloop_kms_requests_total`), every member polls the KMS, `cloop hub doctor` reports `secrets.kms.*`, and a rotation of the KMS key is followed by rewrapping (`TestRewrapFollowsAKMSKeyRotation`, `TestDoctorFailsAnUnreachableKMS`) | A serving process keeps the keys it unwrapped in memory until it exits, so revoking the hub's access at the KMS stops new processes, restores and offline copies at once and running members at their restart. Whoever holds the hub's KMS identity, or administers the KMS key, and a copy of the database opens every secret — that identity is now what the root key was. An outage stops every member that has not yet opened the store and every restore; there is no fallback by design. A backup from before the move still opens with `CLOOP_SECRET_KEY` |
| Sealing key lost | `cloop hub key escrow export` seals `CLOOP_SECRET_KEY` under an operator passphrase — argon2id at RFC 9106's 64 MiB parameters, then AES-256-GCM with every header field as associated data — refuses a passphrase under 15 characters, a key that does not open the hub's sealing keys and a destination inside `.cloop/`, and opens what it wrote before reporting success (`TestWrapOpensWithItsPassphraseOnly`, `TestEveryHeaderFieldIsAuthenticated`, `TestTheFileHoldsNoPlaintext`, `TestEscrowCommandsRefuseWhatCannotRecover`). A crafted file cannot make a verifier allocate more than 4 GiB (`TestParametersAreBoundedOnRead`). The hub records only the escrow's id and the key's fingerprint; `cloop hub doctor` warns while none is recorded and fails when it holds another key than the one in use (`TestTheEscrowOnRecordIsComparedWithTheKeyInUse`) | **Unrecoverable without the escrow and its passphrase**: lose both, or never make one, and every sealed secret is gone. Keys held by a KMS are not in the escrow at all: they are recovered by the KMS key's own durability — soft delete and purge protection on the vault — or not at all (`TestABackupOfAKMSHubRestoresOnlyWithTheKMS`). The escrow is exactly as strong as its passphrase, and offline guessing costs an attacker with the file one argon2id pass per try. The recorded fingerprint, like every checkpoint line, is a passphrase oracle at a PBKDF2 pass per try — harmless for a generated key, not for a typed one |
| State database corrupted or lost | Hot backup (`cloop db backup`) whose sidecar is a sealed manifest — the SHA-256, the sealing keys the backup depends on and its audit head, under an HMAC keyed from `CLOOP_SECRET_KEY` — and a restore preflight that, before swapping anything, checks integrity, schema, digest and seal and that the key derives every sealing key the backup's secrets are sealed under, naming the ones it cannot (`TestTheSidecarIsASealedManifest`, `TestARestoreUnderAnotherKeyIsRefusedBeforeTheSwap`); `cloop db verify`; restore takes a pre-restore copy first. `--accept-secret-loss`, not `--force`, restores anyway, retiring every key the hub would refuse to start on, and is recorded; with no key set it does not apply (`TestAcceptingSecretLossLeavesAHubThatStarts`, `TestAcceptingSecretLossGivesUpEveryKeyTheHubWouldStopOn`). The restore refuses while a hub serves the database, restores only a copy hashing to what the preflight checked, moves the database's `-wal` and `-shm` aside with it so a stale log is not replayed into the restored file, and seals no record of a chain written between the swap and the record (`TestARestoreUnderAServingHubIsRefused`, `TestABackupChangedAfterItsCheckIsNotRestored`, `TestAStaleLogIsNotReplayedIntoTheRestore`, `TestARestoredChainThatChangedIsNotSealed`) | Backups contain sealed secrets — same handling as the database itself. A backup taken without `CLOOP_SECRET_KEY` is unsealed, and `--skip-checksum` or `--allow-unsealed` restore one nothing vouches for |
| Backup edited before it is restored | The sidecar's seal covers its SHA-256, so an edit with the digest recomputed fails the seal, and stripping the seal makes the sidecar unsealed, which is refused without `--allow-unsealed` (`TestAnEditedBackupWithARecomputedDigestIsRefused`); its strings are sealed as written, so a row that is not valid UTF-8 cannot make a sound backup fail its seal (`TestAManifestOfInvalidUTF8StillVerifies`) | Whoever holds `CLOOP_SECRET_KEY` can seal an edited backup's sidecar; whoever can make the operator pass `--skip-checksum` needs no seal at all |
| Shared PVC corrupts SQLite | Replicas share the volume only on one node: the chart adds a required podAffinity term pinning them to the node holding the `ReadWriteOnce` volume, and refuses replicas without persistence or with `ReadWriteOncePod` | Nothing stops an operator from mounting the same volume on another node out of band, or from removing the affinity term by editing the Deployment |

## Out of scope

- **Kernel and hypervisor vulnerabilities.** Container isolation is namespaces
  and cgroups, not a security boundary against a kernel exploit. A
  [Kata sandbox](../guides/kata.md) changes *which* kernel that is — the guest's
  — and adds a hypervisor escape to the chain; it does not put either kernel in
  scope for this document.
- **Malicious LLM provider.** The provider sees prompts, which include task
  context and code excerpts. Treat that as a data-handling decision made when
  choosing a provider.
- **Physical and supply-chain compromise** of the hub host or the images.
- **What the workload does with credentials it legitimately holds.** Grants
  bound the blast radius; they do not constrain intent.
- **Content sent to a destination the policy allows.** The filter decides
  whether a packet leaves, not what is in it, and the proxy does not terminate
  TLS. A sandbox permitted to reach `api.github.com` can push whatever it likes
  there. Byte quotas bound the volume; nothing bounds the meaning.
- **Whether the kernel or the CNI honours the policy that was installed.**
  `nft -f` commits or fails, so the container path is verifiable from an exit
  status. A `NetworkPolicy` is not: cloop cannot tell from the API whether the
  cluster's CNI implements one.
- **Inline styles.** The dashboard's policy keeps `style-src 'unsafe-inline'`:
  the markup is full of `style` attributes, and what injected CSS can do is
  restyle the page — `img-src` and `connect-src` keep it from sending anything
  anywhere but the hub. Removing it is a refactor of every panel's markup with
  no script execution to show for it.
- **Layer 2 and the physical network.** The filter matches destination
  addresses. ARP, DHCP and anything else that never acquires an IP destination
  are outside what it expresses, as is a network the operator attached the host
  to.
